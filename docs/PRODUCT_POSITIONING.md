# Product position and hackathon demonstration

Checked 2026-10-30. Recommendation, not a prediction of placement.

## The job BuildBrief owns

An owner gives an agent a request. A finished-looking screen does not establish
that the rules behind it were implemented. BuildBrief keeps the reviewed request,
the proof for a saved version, the next correction, the human decision, and what
the team has actually demonstrated understanding together.

Use **product acceptance and understanding for AI-built software** as the category.
The plain question is: **Can I accept this work, and do I understand what I own?**
Keep “Know what your AI built” as a short supporting line. Avoid selling an
autonomous fixer, a general code reviewer, a production certification, or a
unique invention. The blueprint's research already identifies overlap with
Spec Kit, Kiro, and Muse Code. Our differentiation is the connected, inspectable
owner workflow and its tested boundaries, not an assertion that competitors
cannot do related work.

New projects start with an idea before Git exists. Existing projects enter by
public GitHub URL or local folder. Both paths require a human to review the
requirements; creating a brief is not building the application.

## Why password recovery is the main demonstration

Recovery is familiar to people who never read code. The original screen looks
reasonable, yet an old link opens recovery. Moving a synthetic clock makes the
omitted policy visible. Users can compare the original and corrected commits,
try fresh/expired/reused links, inspect the unchanged acceptance command, and
follow a requirement to source evidence. Referral remains a secondary case for
scope drift, protected authentication changes, and understanding handover.

[OWASP's Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)
recommends single-use tokens and appropriate expiry. It does not prescribe our
sample's thirty-minute policy. The sample uses deliberate fixtures and a
synthetic account/clock; it is neither real email delivery nor a complete
authentication service.

[Veracode's 2025 report](https://view.ceros.com/veracode/genai-code-security-report2025)
studies generated code against selected weakness categories. It supports
investigating concrete behavioral checks; it does not establish the prevalence
of this reset-policy omission or BuildBrief's effectiveness. Do not reuse its
headline percentage as a marketing claim about this product.

## Fit to the confirmed event

The owner confirmed **Meta Global AI Developer Hackathon / Cerebral Valley**.
The [official public event page](https://dev.meta.ai/events/global-hackathon)
describes Indie judging around creativity, technical ambition, and whether it
works, with **Build for Your World** and **Push the Frontier** themes. The
recommendation remains Indie / Build for Your World: a concrete tool for people
building software with AI. Public descriptions do not establish private scoring
weights, exact video obligations, or participant-only waiver requirements.

No banking/financial integration is justified by the confirmed public event.
The example, idea capture, local connections, and rules checks require no
account or paid model call. Optional provider calls require separately configured
credentials and may cost money; they must be labeled accurately.

## Demonstration sequence

1. Begin with the owner problem: “The agent says done. What did it actually build?”
2. Create a tiny idea brief without a repository. Show the exact context, explicit
   approval, and agent handoff. Do not pretend the handoff generated the app.
3. Switch to Lighthouse. Open an old recovery link in the original build, then
   in the correction. Show a fresh link still works. Identify the seeded conditions.
4. Open the acceptance brief: failed acceptance stays unresolved; fresh passing
   checks support the corrected version. Open one immutable source citation.
5. Prepare a bounded correction request and record a synthetic review decision.
   Explain that review and automated findings remain separate.
6. Use the referral case to show possibly unrequested authentication changes and
   role-specific understanding. Answer a real source-location question; open
   explanations await a human grade, and unassessed understanding stays unmeasured.
7. Show a real public repository import or local connection. Keep private data
   out of a recorded demo.

Muse Code is a complementary workstream. Use the scoped prompt in
MUSE_PARALLEL_PROMPT.md to validate native capture. A handler unit test is not
proof of a real hook. A coding session using Muse Spark is not proof that
BuildBrief's optional Meta API provider was used. Only demonstrate what the
actual run records.

Before submission: verify the participant portal/waiver, test with an unfamiliar
person, validate any explicitly budgeted live model use, rehearse the evidence
story, and record the actual interaction. These are competition preparation
actions, not claims of completion or guaranteed placement.
